Версия 1.0. Документ предназначен для передачи ИИ-агенту-разработчику (Cursor, Claude Code, Antigravity). Юридические разделы нужно проверить у юриста заказчика до запуска.

# 1. Цель и контекст

Веб-сервис, где пользователь создаёт красивую цифровую визитку (публичная страница с контактами, ссылками и брендингом), делится ею по ссылке, QR-коду или NFC-метке. Метка — наклейка на телефон или карту, как платёжные стикеры. При касании чужой телефон открывает страницу визитки в браузере, приложение ставить не нужно.

Монетизация — подписка. Референс по идее и визуалу: nfsea.ru.

**Главные принципы:**

- NFC-метка хранит только короткую ссылку, а не данные. Данные меняются, метка остаётся прежней.
- Визитка публикует персональные данные, поэтому приватность и согласия — ключевая часть продукта.
- Безопасность и соответствие законам РФ — требование, а не пожелание (разделы 8 и 9).

# 2. Роли

| Роль | Описание |
|---|---|
| Гость | Открывает публичные визитки, регистрируется |
| Пользователь (тариф «Обычный») | Одна своя визитка |
| Пользователь Pro (админ компании) | Своя визитка + управление компанией и визитками сотрудников |
| Сотрудник | Пользователь с тарифом «Обычный», состоящий в компании Pro-админа |
| Администратор платформы | Сотрудник заказчика: модерация, поддержка, аналитика |

# 3. Тарифы

**Обычный:** 1 визитка, выбор из набора шаблонов, ссылка и QR, NFC-привязка, базовая статистика (просмотры), скачивание vCard.

**Pro:** всё из «Обычного» + компания, приглашение сотрудников (лимит мест задаётся в конфиге тарифа), управление визитками сотрудников, единый брендинг компании (логотип, цвета, шрифт, обязательный блок), собственный короткий адрес визитки, расширенная статистика, экспорт списка ссылок для массовой записи меток, запись действий в журнал аудита компании.

**Правила (допущения, см. раздел 12):**

- Лимиты, цены и количество мест хранятся в БД и настраиваются из админки платформы, а не в коде.
- Сотрудник может быть в одной компании одновременно.
- Если сотрудник выходит из компании, его визитка остаётся у него, брендинг компании снимается.
- При окончании Pro: 7 дней льготного периода, затем компания замораживается: сотрудники теряют связь с компанией, но их визитки продолжают работать как «Обычные». Данные не удаляются.
- Если у пользователя «Обычного» тарифа подписка закончилась, визитка 14 дней доступна, затем публичная страница показывает заглушку «Визитка временно недоступна». Данные хранятся 90 дней.

# 4. Функциональные требования

## 4.1 Регистрация и вход

- Регистрация по email + пароль, подтверждение email обязательно.
- Опционально (этап 3): вход через VK ID и Яндекс ID.
- Восстановление пароля по одноразовой ссылке (срок жизни 30 минут, токен хранится хэшем).
- 2FA (TOTP) обязательна для администраторов платформы и админов компаний Pro, опциональна для остальных.
- Удаление аккаунта и выгрузка своих данных (JSON) из личного кабинета.
- При регистрации обязательны отдельные чекбоксы: согласие на обработку ПДн, принятие оферты. Предзаполненных чекбоксов быть не должно.

## 4.2 Редактор визитки

- Поля: имя, должность, компания, описание, фото/аватар, обложка, телефон(ы), email(ы), сайт, адрес, мессенджеры (Telegram, WhatsApp, MAX, VK), соцсети, произвольные ссылки с подписью, график работы.
- Для каждого поля переключатель «показывать на публичной странице».
- Выбор шаблона, цветовой схемы, шрифта (шрифты хранятся локально, без Google Fonts).
- Живой предпросмотр на мобильном и десктопном размере.
- Загрузка изображений: до 2 МБ аватар, до 3 МБ обложка, форматы JPEG/PNG/WebP, без SVG.
- Валидация ссылок: разрешены только схемы https, http, tel, mailto. Все остальные отклоняются (защита от javascript:).
- Публикация/снятие с публикации одним переключателем.

## 4.3 Публичная страница визитки

- Адрес вида `https://домен/c/{slug}`, slug — случайная строка 8–10 символов; в Pro можно задать свой читаемый slug (уникальный, с проверкой на зарезервированные слова).
- Адаптивная, быстрая (LCP до 2,5 с на мобильной сети), без обязательной регистрации для просмотра.
- Кнопки: «Сохранить в контакты» (скачивание vCard 3.0 с `Content-Disposition`), позвонить, написать, открыть ссылку, поделиться, показать QR.
- Мета-теги Open Graph для красивого превью в мессенджерах.
- По умолчанию `noindex`. Владелец может включить индексацию.
- Ссылка «Пожаловаться» (форма жалобы с причиной).
- Защита от парсинга: rate limit по IP, без отдачи контактов в HTML для известных ботов (по желанию заказчика).

## 4.4 NFC и QR

- Метки: NTAG213/215/216 (или совместимые). Запись: один NDEF URI-record `https://домен/c/{slug}?s=nfc` (параметр нужен для статистики).
- Страница «Записать на NFC-метку» в кабинете:
  - пошаговая инструкция для iPhone и Android (через приложение NFC Tools или аналог);
  - на Android в Chrome — кнопка записи через Web NFC (`NDEFReader.write`), только по HTTPS и по клику пользователя; на iOS и в других браузерах кнопку не показывать;
  - предупреждение о необратимости, если пользователь решит заблокировать метку от перезаписи;
  - копирование ссылки одним нажатием.
- Генерация QR (SVG и PNG) для визитки, с возможностью скачать в высоком разрешении.
- В Pro: экспорт CSV со ссылками всех визиток компании для массовой записи меток.
- Метка не содержит ПДн: только URL.

## 4.5 Компании (Pro)

- Создание компании при покупке Pro: название, логотип, фирменные цвета, сайт.
- Приглашение сотрудника по email. Приглашение — одноразовая ссылка со сроком жизни 7 дней.
- Сотрудник, принимая приглашение, видит экран: «Компания X сможет редактировать и отключать вашу визитку» и явно соглашается. Без согласия присоединения нет.
- Если сотрудник ещё не зарегистрирован, он регистрируется по приглашению (тариф «Обычный»). Оплата тарифа сотрудника засчитывается местом в Pro-подписке админа, отдельно платить не нужно.
- Админ компании может: создавать визитку за сотрудника (до принятия он видит её как черновик), редактировать визитки сотрудников, включать/отключать их, применять брендинг, отвязывать сотрудника, менять слоты.
- Сотрудник видит, что визитка управляется компанией, и может выйти из компании в любой момент.
- Все действия админа над чужими визитками пишутся в журнал аудита (кто, что, когда), журнал виден сотруднику применительно к его визитке.
- Передача владения компанией и удаление компании — отдельные подтверждаемые действия.

## 4.6 Подписка и оплата

- Платёжный провайдер РФ с поддержкой рекуррентных платежей и 54-ФЗ (по умолчанию ЮKassa; интеграция через адаптер, чтобы провайдера можно было заменить).
- Периоды: месяц и год (скидка за год задаётся конфигом).
- Автопродление включается только с явным согласием, отключается в один клик в кабинете. Перед списанием — уведомление по email за 3 дня.
- Фискальные чеки отправляются автоматически покупателю.
- Webhook-и платёжной системы: проверка подписи/IP-адресов, идемпотентность по id платежа, обработка повторов и пропусков.
- Состояния подписки: trial (опционально), active, past_due (льготный период), canceled, expired.
- Возвраты: только через админку платформы, с записью в журнал.
- Данные карт сервис не видит и не хранит, используется токен провайдера.

## 4.7 Статистика

- Просмотры визитки по дням, источники (NFC / QR / ссылка по параметру `s`), клики по кнопкам, скачивания vCard.
- Без cookie и сторонних трекеров: события считаются на сервере, IP не хранится (только хэш с ежесуточной солью, для подсчёта уникальных).
- Pro: сводка по компании и по каждому сотруднику.

## 4.8 Админка платформы

- Список пользователей, компаний, подписок и платежей; блокировка и разблокировка.
- Очередь жалоб: скрыть визитку, заблокировать автора, ответить заявителю.
- Настройка тарифов, лимитов, шаблонов, зарезервированных slug.
- Журнал аудита всех админских действий. Вход только с 2FA.

## 4.9 Уведомления

- Email: подтверждение, сброс пароля, приглашение, чек, предупреждение о продлении, уведомление о входе с нового устройства.
- Рекламные рассылки — только при отдельном согласии, со ссылкой на отписку в каждом письме.

# 5. Модель данных (основные сущности)

`users`, `sessions`, `email_tokens`, `totp_secrets`, `companies`, `memberships` (user, company, role: owner|member, status), `invitations`, `cards` (owner, company nullable, slug, template, theme, published, deleted_at), `card_fields` (card, type, label, value, visible, sort), `plans`, `subscriptions`, `payments`, `consents` (user, type, document version, timestamp, IP, user agent), `card_events` (агрегаты по дням), `reports`, `audit_logs`, `files`.

Требования: UUID вместо автоинкремента в публичных API, soft delete для визиток с физическим удалением по расписанию, миграции только через инструмент миграций, индексы на slug, owner, company.

# 6. Страницы и API

**Страницы:** главная/лендинг с тарифами, вход, регистрация, кабинет (визитка, редактор, NFC, статистика, настройки, подписка), кабинет компании, админка платформы, публичная визитка, оферта, политика обработки ПДн, согласия, 404 и страницы ошибок.

**API:** REST или серверные действия фреймворка; все эндпоинты проверяют аутентификацию и права на уровне владения ресурсом (защита от IDOR). OpenAPI-описание для REST-части. Единый формат ошибок.

# 7. Нефункциональные требования

- Языки: русский (основной), структура под добавление английского.
- Адаптивность: mobile-first, поддержка Safari iOS 16+, Chrome/Edge/Firefox/Yandex Browser последних двух лет. А также веб-версия на ПК.
- Производительность: публичная страница рендерится на сервере или статически с кэшем; p95 ответа до 300 мс.
- Доступность: контраст WCAG AA, управление с клавиатуры в кабинете.
- Надёжность: доступность 99,5%, ежедневные резервные копии, хранение 30 дней, проверка восстановления перед запуском.
- Наблюдаемость: структурированные логи без ПДн, health-эндпоинты, алерты на 5xx и ошибки платежей.
- Покрытие тестами критичной логики (права, платежи, подписки) не ниже 80%.

# 8. Требования безопасности

Ориентир: OWASP ASVS уровень 2 и OWASP Top 10.

- Пароли: argon2id, минимум 10 символов, проверка по списку утёкших паролей (локальный список).
- Сессии: серверные, cookie `HttpOnly; Secure; SameSite=Lax`, ротация при входе, отзыв всех сессий в настройках.
- Защита от перебора: rate limit на вход, регистрацию, сброс пароля, форму жалоб; задержки и временная блокировка; одинаковые ответы, чтобы нельзя было узнать, зарегистрирован ли email.
- CSRF-защита всех изменяющих запросов; строгий CORS.
- Заголовки: HSTS, строгий CSP (без inline-скриптов), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors 'none'` для кабинета.
- Валидация входных данных на сервере схемами (zod или аналог), экранирование вывода, запрет произвольного HTML и Markdown-ссылок с опасными схемами в пользовательских текстах.
- Ссылки пользователей на публичной странице: `rel="noopener noreferrer nofollow ugc"`.
- Загрузки файлов: проверка реального MIME по содержимому, лимиты размера, перекодирование изображений (sharp), удаление EXIF и геометок, случайные имена файлов, отдельный домен или бакет без выполнения кода.
- Разграничение доступа: роли + проверка принадлежности ресурса компании на каждом запросе; автотесты на IDOR для каждого эндпоинта.
- Секреты только в переменных окружения или менеджере секретов, в репозитории их нет; `.env.example` без реальных значений.
- Шифрование: TLS 1.2+ везде, шифрование дисков и бэкапов, TOTP-секреты шифруются на уровне приложения.
- Журнал аудита: вход, смена пароля и email, права, действия админов, возвраты, экспорт данных. Логи неизменяемы для приложения.
- Зависимости: фиксация версий, автоматическая проверка уязвимостей в CI (npm audit / Trivy), сканирование секретов в коммитах, SAST (Semgrep).
- Инфраструктура: Docker, минимальные образы, запуск не от root, закрытые порты БД и Redis, WAF и защита от DDoS на уровне провайдера.
- Процесс: план реагирования на инциденты, в том числе уведомление Роскомнадзора об утечке ПДн (раздел 9).

# 9. Соответствие законодательству РФ

Ниже перечень требований, которые должны быть учтены в продукте и процессах. Это не юридическая консультация: заказчику нужно согласовать документы и процессы с юристом.

**Персональные данные (152-ФЗ):**

- Оператором ПДн является юридическое лицо или ИП заказчика. До запуска подать уведомление об обработке ПДн в Роскомнадзор.
- Опубликовать на сайте политику обработки ПДн (доступна с каждой страницы и из форм сбора данных).
- Согласие на обработку ПДн оформляется отдельным документом, а не частью оферты или пользовательского соглашения. Хранить факт согласия: версия текста, время, IP, браузер (таблица `consents`).
- Визитка публикует ПДн неограниченному кругу лиц, поэтому нужно отдельное согласие на распространение ПДн (ст. 10.1): пользователь сам выбирает, какие данные открыть, в соответствии с переключателями видимости полей. Для сотрудника такое согласие даёт он сам при принятии приглашения, админ компании не может давать его за него.
- Права субъекта: просмотр, исправление, удаление, выгрузка, отзыв согласия — из кабинета, плюс форма обращения. Срок ответа на обращения учесть в регламенте.
- Сроки хранения: после удаления аккаунта ПДн удаляются в разумный срок (по умолчанию 30 дней, бэкапы ротируются), платёжные документы хранятся по требованиям бухучёта.
- Определить уровень защищённости ИСПДн по Постановлению Правительства № 1119, состав мер по приказу ФСТЭК № 21; подготовить модель угроз и внутренние документы (приказ о назначении ответственного, перечень лиц с доступом). Разработка техдокументации — на стороне заказчика.
- Инцидент с утечкой ПДн: уведомление Роскомнадзора в установленные законом сроки; в продукте должен быть процесс выявления и запись о каждом инциденте.

**Локализация (242-ФЗ):**

- Первичная запись и хранение ПДн граждан РФ — только в базах на территории РФ. Хостинг и объектное хранилище: российский провайдер (Selectel, Yandex Cloud, VK Cloud, Timeweb Cloud или аналог).
- Не использовать зарубежные сервисы, получающие ПДн пользователей: Google Analytics, Google Fonts, reCAPTCHA, зарубежные CDN, Sentry Cloud, SendGrid, Mailchimp и подобные. Альтернативы: шрифты локально, Yandex SmartCaptcha, self-hosted GlitchTip или Sentry, российские почтовые и SMS-сервисы (Unisender, Yandex Cloud Postbox, SMS.ru или аналог).
- Если трансграничная передача всё же нужна, она оформляется отдельно по ст. 12 152-ФЗ.

**Cookie и аналитика:** баннер согласия на нефункциональные cookie. Технические cookie (сессия, CSRF) работают без согласия. Яндекс.Метрика — только после согласия, если заказчик захочет её подключить.

**Платежи и торговля:**

- Публичная оферта: реквизиты продавца, описание тарифов, порядок оплаты, продления, отказа и возврата; положения о возврате соответствуют закону о защите прав потребителей.
- 54-ФЗ: кассовые чеки при каждом платеже (через интеграцию платёжного провайдера с онлайн-кассой).
- Автопродление: отдельное согласие, понятные условия и простая отмена.

**Реклама:** рассылки рекламного характера — только с согласия, с возможностью отписки (38-ФЗ «О рекламе»).

**Контент пользователей (149-ФЗ):** сервис хранит пользовательский контент, поэтому нужны: правила использования с перечнем запрещённого содержимого, форма жалоб, процесс проверки и удаления/скрытия нарушающих визиток, реагирование на требования Роскомнадзора и правоохранительных органов, журнал обращений.

**Документы, которые нужно подготовить заказчику** (шаблоны текстов агент может положить в `/legal` как заглушки, помеченные «согласовать с юристом»): политика обработки ПДн, согласие на обработку ПДн, согласие на распространение ПДн, пользовательское соглашение/оферта, политика cookie, правила размещения контента.

# 10. Технологии и инфраструктура (рекомендации)

- Фронтенд и бэкенд: Next.js (App Router) + TypeScript; стили: Tailwind CSS; шаблоны визиток — набор React-компонентов.
- БД: PostgreSQL 16, ORM Prisma или Drizzle, миграции в репозитории.
- Кэш и rate limit: Redis.
- Файлы: S3-совместимое хранилище российского провайдера.
- Фоновые задачи: очередь (BullMQ) для писем, платежей, очистки данных.
- QR: библиотека генерации на сервере (SVG).
- Контейнеризация: Docker Compose для разработки, Dockerfile для продакшена; reverse proxy Caddy или Nginx.
- CI/CD: GitHub Actions или GitLab CI: линт, типы, тесты, аудит зависимостей, сборка образа.
- Тесты: Vitest (юнит), Playwright (e2e: регистрация, создание визитки, покупка Pro, приглашение сотрудника).
- Допускается замена стека, если агент обоснует и сохранит все требования разделов 7–9.

# 11. Этапы и критерии приёмки

**Этап 1. Основа.** Репозиторий, Docker, CI, схема БД и миграции, регистрация и вход, подтверждение email, сессии, rate limit, согласия. *Приёмка:* пользователь регистрируется, подтверждает email, входит, выходит, сбрасывает пароль; тесты проходят.

**Этап 2. Визитка.** Редактор, шаблоны, загрузка изображений, публичная страница, vCard, QR, видимость полей, жалобы. *Приёмка:* визитка открывается по ссылке с телефона, vCard добавляется в контакты, опасные ссылки отклоняются.

**Этап 3. NFC.** Страница записи метки, Web NFC на Android, инструкции, параметр источника, статистика просмотров. *Приёмка:* метка с записанной ссылкой открывает страницу на iPhone и Android; переходы с NFC попадают в статистику.

**Этап 4. Подписки и платежи.** Тарифы, оплата, webhook-и, чеки, автопродление и отмена, льготный период, ограничения по тарифу. *Приёмка:* в тестовом контуре провайдера проходят покупка, продление, отмена, неуспешный платёж; повторный webhook не создаёт дублей.

**Этап 5. Компании.** Pro-компания, приглашения, управление визитками сотрудников, брендинг, журнал аудита, экспорт ссылок. *Приёмка:* админ редактирует визитку сотрудника, сотрудник видит запись в журнале и может выйти; админ другой компании не имеет доступа (автотест на изоляцию).

**Этап 6. Админка платформы, юридические страницы, усиление безопасности.** Модерация, юридические страницы, баннер cookie, выгрузка и удаление данных, проверка по списку из раздела 8, нагрузочный тест. *Приёмка:* пройден чек-лист безопасности, внешний аудит зависимостей без критичных уязвимостей, восстановление из бэкапа проверено.
